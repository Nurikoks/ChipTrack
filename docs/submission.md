# Сдача решения — ChipTrack (ForteBank Datathon 26)

Локальный AI-сервис, который по видео кассового рабочего места ищет визуальные признаки возможных нарушений
кассовой дисциплины и показывает проверяющему вердикт, таймкоды, кадры-доказательства, описание и нормативное основание.
Результат — подсказка для проверки человеком, а не юридическое или дисциплинарное заключение.

Документ построен по разделу 8 кейса («Что команда должна представить»). Подробности — по ссылкам.

## 1. Адреса и доступ

| Что | Адрес |
|---|---|
| Веб-интерфейс | `https://<адрес-сервиса>/` |
| API: загрузка видео | `POST https://<адрес-сервиса>/api/v1/analyze` (multipart, поле `file`) |
| API: статус и результат | `GET https://<адрес-сервиса>/api/v1/jobs/{job_id}` |
| Проверка живости | `GET https://<адрес-сервиса>/health` |
| API-ключ | передаётся жюри отдельно, вместе с адресом (в репозитории его нет); заголовок `X-API-Key` |

```bash
curl -X POST https://<адрес-сервиса>/api/v1/analyze -H "X-API-Key: <ключ>" -F "file=@video_017.mov"
curl https://<адрес-сервиса>/api/v1/jobs/<job_id> -H "X-API-Key: <ключ>"
```

* Формат ответа строго по разделу 10 кейса (`job_id`, `status`, `verdict`, `violations[]` с `type`, `timecode_sec`,
  `description`, `evidence_frames` из 1–3 JPEG в base64). Дополнительные поля (`type_id`, `confidence`, `rule`,
  `partial`, `warnings`, `video_duration_sec`) только добавлены и ничего не заменяют.
* Запросы без верного ключа → `401` (особенность туннеля для больших файлов без ключа — в README, «Публичный URL»). Каждая задача завершается (`done` или `failed`) не позже чем через 5 минут
  от начала загрузки: жёсткий срок 270 с, затем возвращается лучший частичный результат с `partial: true`.
* Задачи жюри (с ключом) идут в очереди раньше задач веб-интерфейса.
* Сервис работает на машине команды (RTX 4060 Laptop 8 ГБ), публичный адрес даёт туннель ngrok — он только
  пересылает HTTP-трафик. Видео, кадры и описания не передаются ни в какие облачные AI-сервисы: все модели
  выполняются локально.

## 2. Запуск и использование

Полная инструкция — [README.md](../README.md), раздел 1. Кратко:

1. Окружение Python 3.11+, `pip install -r requirements.txt` (PyTorch cu128).
2. Один раз скачать веса: `scripts\download_weights.py` (нужен интернет). Дальше сервис работает офлайн
   (`HF_HUB_OFFLINE=1`).
3. `scripts\start_service.ps1 -Port 8000` — при первом запуске генерирует API-ключ в `runtime\api_key.txt`.
4. Публичный адрес: `ngrok http 127.0.0.1:8000` (подробности и известные особенности — README, «Публичный URL»).

Адрес сервиса и ключ в репозитории не публикуются: репозиторий открытый, а веб-интерфейс по условиям кейса работает
без авторизации. Они переданы жюри вместе с решением.

Веб-интерфейс: перетащить видео (.mov/.mp4) → статус обработки → вердикт «Нарушение не обнаружено» или
«Обнаружены признаки возможных нарушений», для каждого нарушения — тип, таймкод, описание, кадры и правило со
ссылкой на adilet.zan.kz. Клик по таймкоду перематывает видео к событию. Все проверки сохраняются в истории слева
(только в браузере проверяющего), к прошлым результатам можно вернуться одним кликом.

## 3. Архитектура, подход и модели

Подробно — [docs/architecture.md](architecture.md).

Размеченных примеров мало (21 видео с нарушениями на 12 типов), а тест снят с другого ракурса, поэтому модель
не обучается end-to-end. Каждый тип нарушения — это **триггер** (отношение людей и объектов сцены во времени) плюс
**узкая визуальная проверка да/нет** на нужном фрагменте кадра:

```
видео → кадры 2 fps → детекция людей (RT-DETRv2) → поиск стола, сейфа, ноутбука и двери на этом видео (Qwen3-VL)
      → трекинг и события (ушёл с места, вошёл человек, смена клиента) → вопросы да/нет к VLM по кропам
      → нарушения с таймкодом и кадрами → правило из реестра → вердикт
```

* Объекты сцены находятся заново на каждом видео — нет фиксированных пиксельных зон, решение не привязано к ракурсу.
* Каждый вывод подтверждён явным ответом модели на кадре-доказательстве; описание говорит только о том, что видно.
* Новый тип нарушения = один вопрос + один триггер + одна запись в реестре правил, без переобучения.

| Компонент | Модель / библиотека | Лицензия |
|---|---|---|
| Детектор людей и предметов | `PekingU/rtdetr_v2_r18vd` (RT-DETRv2, COCO) | Apache-2.0 |
| Визуально-языковая модель | `Qwen/Qwen3-VL-2B-Instruct`, 4-bit (≈1,6 ГБ VRAM) | Apache-2.0 |
| Сервис | FastAPI, uvicorn, PyTorch, transformers, OpenCV | MIT / BSD / Apache-2.0 |

Все компоненты open source с лицензиями, разрешающими коммерческое использование. Отклонены: Ultralytics YOLO
(AGPL-3.0), Qwen2.5-VL-3B (исследовательская лицензия), любые облачные API.

## 4. Нормативные источники и сопоставление с видео

Подробно — [docs/normative_sources.md](normative_sources.md), машиночитаемый реестр —
[data/rules_registry.json](../data/rules_registry.json). Сервис цитирует **только** пункты из реестра.

| Документ | Акт | Ссылка |
|---|---|---|
| Правила осуществления кассовых операций и операций по инкассации банкнот, монет и ценностей в банках второго уровня | пост. Правления НБРК от 29.11.2019 № 231 | https://adilet.zan.kz/rus/docs/V1900019680 |
| Правила организации охраны и устройства помещений банков второго уровня | пост. Правления НБРК от 24.02.2020 № 14 | https://adilet.zan.kz/rus/docs/V2000020075 |
| Требования к обеспечению информационной безопасности банков | пост. Правления АРРФР от 03.04.2026 № 53 | https://adilet.zan.kz/rus/docs/V2600038336 |

Каждый пункт сверен дословно с текстом на adilet.zan.kz (17.10.2026). Утратившие силу акты (пост. НБРК № 48
от 2018 г., кассовые правила 1999/2001 гг.) проверены и исключены.

**Принцип сопоставления:** видимый факт на кадре → тип нарушения → пункт правила из реестра → текст описания.
Уровень основания указан явно: «Правило» (прямое), «Возможное нарушение требований» (среднее),
«Косвенно связано с требованием» (по толкованию). Если основание не найдено, сервис так и пишет и документ не называет.
Сервис не делает выводов о том, чего не видно на видео (проводки, сверки, содержимое документов).

## 5. Перечень распознаваемых типов нарушений

| Код | Тип (как в поле `type`) | Что ищет сервис | Основание (уровень) |
|---|---|---|---|
| T01 | Ценности/документы оставлены без присмотра на рабочем месте | работник отходит, на столе остаются банкноты, инкассаторская сумка или документы | НБРК № 231, п. 20 ч. 2 (среднее) |
| T02 | Рабочее место покинуто без блокировки компьютера | никого нет за столом, на экране ноутбука рабочее содержимое | АРРФР № 53, п. 71 пп. 9 (косвенное) |
| T03 | Сейф оставлен открытым без присмотра | дверца сейфа открыта, рядом никого | НБРК № 231, п. 20 ч. 2; п. 80 (среднее) |
| T04 | Ключ оставлен в замке сейфа | ключ в замке, работник отошёл | НБРК № 231, п. 80 (среднее) |
| T05 | Наличные предыдущей операции оставлены открыто при подходе следующего клиента | на столе пачка банкнот, когда подходит следующий человек | НБРК № 231, п. 20 ч. 2 (прямое) |
| T06 | Постороннее лицо в кассовой зоне | рядом с работником на его стороне стола стоит ещё один человек | НБРК № 14, п. 8; п. 16 пп. 1 (среднее) |
| T07 | Дверь кассового помещения не закрыта | человек вошёл, дверь осталась открытой | НБРК № 14, п. 8; п. 16 пп. 1 (среднее) |
| T08 | Пересчёт наличных клиента в его отсутствие | клиент ушёл, затем работник пересчитывает наличные | НБРК № 231, п. 20 ч. 1; п. 31 пп. 4 (прямое) |
| T09 | Приём сумки у инкассатора без видимой проверки документов | инкассатор с сумкой, передачи документа не видно | НБРК № 231, п. 24 (прямое) |
| T10 | Личные вещи на рабочем месте кассира | куртка, сумка на кассовом столе | НБРК № 231, п. 12 ч. 1 (прямое) |
| T11 | Употребление напитков/пищи на рабочем месте | работник пьёт за столом с наличными | НБРК № 231, п. 12 ч. 2 (по толкованию) |
| T12 | Передача банкнот клиенту у кассового стола | банкноты передаются через стол | не верифицировано — требует оценки проверяющим |

Подробное описание каждого типа с кадрами — [taxonomy.md](../taxonomy.md).

## 6. Качество, ограничения и известные ошибки

**Качество на 40 обучающих видео** (in-sample: пороги подобраны на этих же видео, цифры оптимистичны) —
[docs/evaluation.md](evaluation.md):

| Набор | Recall | Precision | Тип угадан | Медиана ошибки таймкода | Время на видео |
|---|---|---|---|---|---|
| исходный ракурс | 0,86 (18/21) | 0,67 | 18/22 | 1,9 с | ≈26 с |
| искусственно изменённый ракурс (перспектива, поворот, отражение, кроп, альбомная ориентация) | 0,81 (17/21) | 0,68 | 14/21 | 2,1 с | ≈23 с |

Выбран режим «лучше лишний просмотр, чем пропуск»: ложная тревога стоит проверяющему одного взгляда,
пропущенное нарушение не увидит никто.

**Ограничения и известные ошибки** (полный список — [docs/architecture.md](architecture.md), раздел 7):

* **T04 ключ в замке** почти не обнаруживается: ключ занимает 3–5 пикселей на этом расстоянии.
* **T12 передача банкнот** срабатывает почти на каждой операции с клиентом — модель не отличает нарушение от штатной
  выдачи; это основной источник ложных тревог.
* **T06 посторонний** иногда срабатывает, когда к столу просто подходит клиент.
* **T07 дверь**: состояние стеклянной двери модель различает плохо.
* **T09 инкассатор** включён по умолчанию (приоритет полноты) и срабатывает и на штатной процедуре.
* Маленькая пачка банкнот на загромождённом столе может быть пропущена; в тёмных сценах хуже читаются экраны и сейф.
* Таймкоды «ухода с места» имеют разброс ±2 с.
* Сильный поворот или перспектива снижают качество (см. таблицу выше); на настоящем новом ракурсе решение не проверялось.
* Сервис не утверждает нарушение там, где нужны невидимые данные (проводки, сверки, содержимое документов),
  и не распознаёт лица.

## 7. Приватность

* Сервер не хранит видео: файл удаляется сразу после обработки, результаты держатся в памяти 6 часов.
* Веб-интерфейс хранит историю проверок (видео и кадры) только в браузере проверяющего, до удаления.
* Без облачных AI-сервисов; после загрузки весов интернет для обработки не нужен — решение переносимо во внутренний
  контур банка.
